## 二、未闭环问题（按严重度）

### 高：OpenCode filesystem MCP 可绕过 subagent 写入边界

机器 B 的真实工具调用证明，`filesystem_write_file` 落入 agent 的通配允许规则，可在 `verify` 允许目录之外写入 `协作/state-overrides/冒烟测试.json`。现有 `edit: deny` 只限制内置编辑工具，没有限制这个 MCP 工具；报告说明 `execute` 与 `verify` 均受影响。

因此，`.opencode/agent/execute.md` 所称“仅可写指定目录”和 `.opencode/agent/verify.md` 所称“只读（除验证报告）”目前不是运行时硬边界。Git hooks/CI 能检查形成的提交，但不能阻止 agent 在提交前改动工作区，也不能替代工具权限隔离。D-20260811-010 已记录“用户决定暂不修复”，故本次不擅自改动；风险仍应保持为开放状态，不能在验收中称为闭环。

### 高：历史补登记声明与校验器行为矛盾

D-20260811-010 和 00 卷新增行称已为 5 个历史 commit 完成补登，但用原审查基线复验：

```text
python3 scripts/workflow.py validate --base 5ed13b5 --head af35e34
```

仍对 `0320d508931e`、`563526559106`、`9d36aefb5d68`、`5bc7c0749f31`、`e178b8f0e720` 全部报“必须同 commit 更新结构化决策 JSON”。原因是 `validate_commit_rules` 只读取被检查 commit 自身新增的决策 JSON，不识别后续补登；当前 decision schema 也没有绑定历史 commit SHA 的例外字段。

当前校验和 CI 之所以绿色，是因为通常只检查 `ac49e10..af35e34` 等新范围，未再次覆盖上述历史提交。这不是历史债务已被程序化消除。项目规则一方面允许历史遗留补登，另一方面校验器拒绝任何后续补登，二者需通过新的结构化、精确 SHA 绑定机制或明确保留历史红线来统一；在用户拍板前不应自行放宽“同 commit”铁律。

### 中：Windows 回归保护仍不完整

1. GitHub Actions 只有 `ubuntu-latest`；现有任务分配测试能在 Windows 暴露路径问题，但 Linux CI 不会覆盖 Windows 路径语义。
2. 仓库没有 `.gitattributes`。三个 `.githooks/*` 当前入库内容是 LF，机器 B 本次亦成功启用 hooks，但新 Windows clone 在 `core.autocrlf=true` 下仍有 shell hook 被检出为 CRLF 的风险。
3. README/AGENTS 未写明代码语法所需的 Python 3.10+；机器 B 的 3.12.10 满足要求，但新机器就绪检查缺少这一项。

建议后续在用户确认后加入 Windows CI job、用 `.gitattributes` 固定 `.githooks/*` 为 LF，并记录最低 Python 版本。它们不否定本次 B 机实测结果，但决定未来能否持续防回归。
