## 二、确定性问题（按严重度）

### 高：T-028 的 outputs/max_files 与 1081 个生成文件矛盾，交接必败

`任务书/T-028.json` 声明输出目录 `mod/history/states/` 且 `max_files=3`；但 `task_handoff` 对任务书 outputs 使用文件路径**精确集合比较**，不会把尾随 `/` 当目录前缀。根据当前快照模拟，1081 个实际生成路径全部落在 declared outputs 之外，同时文件数 1081 > 3。

结论：即使机器 A 正确完成 dry-run、生成和加载测试，也无法通过当前 handoff。必须在领取 T-028 前统一“目录型 output”的匹配语义，并把 max_files 改为与 1081 个 state 文件相容的限制（或另设 max_generated_files）。静态校验应增加一个针对现有任务书的可交付性检查。

### 高：T-028 的加载测试不是状态机硬门禁

T-028 的 `required_capabilities` 缺少 `load_test`；`task validation-result` 是否进入 `pending_test` 依赖主调度器手工传 `--requires-load-test`，校验器没有根据任务书 acceptance 强制该参数。故 T-028 可被错误地从验证直接送入 `ready_to_merge`，跳过任务书要求的实机加载测试。

应把 `load_test` 加入 T-028 能力要求，并让工作流从任务书的机器可读字段决定是否必须测试，而不是依赖命令行自觉。

### 高：T-009 未实现已确认的建筑槽扩展，却已标记 done

D-20260812-009/010 明确要求在 T-009 实现 `common/state_category` 覆盖或等效槽位扩展；仓库中没有相关文件，T-009 的任务书和验证报告也把“基础设施扩展”误写成了 override 字段合并。当前若生成，部分单州将写入五十余座工厂，远超决策所指的原版槽位约束。

此外，T-009 的目标断言是“各国工厂总数 = 2000 × 工业份额”，scope 包含 JAP，但实际仅生成 1904 座并把日本应有的 15 座全部省略；验证报告明确记录“日本无核心州未分配（15 座）”后仍判 PASS。这不是“船坞归零”，而是整个国家工厂归零。

D-20260812-009 的 JSON 还写“大顺约 150—180 厂”，而同名 Markdown 与 16—18% × 2000 均为 320—360；当前数据为 340。机器可读权威记录存在数字笔误。

结论：T-009 应重开或新增补完任务；完成槽位机制、修正日本 15 厂处理，并统一 JSON/Markdown 后才能作为 T-028 前置依赖。

### 高：项目声明“新建”的 tag 尚无项目内定义，T-028 缺少国家层前置

映射表列出 13 个“新建 tag”，地域 override 已实际使用 KOR/VIE/JOH/IND/BUK/KHV/KAZ/ZAN/FNA/XIN/XYN 等；但 `mod/common/country_tags/`、`mod/common/countries/`、`mod/history/countries/` 仍只有 `.gitkeep`。T-028 的依赖中也没有“国家/tag 实现”任务。

因此仓库本身不能保证生成 state 中引用的 tag 均已注册并具有国家历史。若依赖某些新版原版 tag，必须由机器 A 对当前 1.19.2 tag 表受控核实；对真正自定义 tag 必须先建项目文件。否则 T-028 的加载测试很可能因未知/未初始化 tag 失败，即使 state 文本本身语法正确。

### 高：T-006 实际只有领导人施工框架，却被标记 done

D-20260811-014 要求 20 国每国 1—3 名核心人物及姓名/职务/派系/背景；`设定书/10-命名卷.md` 当前只有“预计人数、来源策略、备注”的计划表，并明确写“具体人设由 T-006 执行/各主题阶段填充”。`tasks.json` 却将 T-006 标为 done。

这会让下游误以为领导人内容已经完成。应把 T-006 恢复为 todo/分拆状态，或把任务名称改为“领导人范围与生成规则确认”并另建实际人物任务。

### 高：重大内容决策的审计记录存在主 agent 自我确认

当前有 11 份 `status=confirmed` 的决策记录，其 `confirmed_by` 不是 user。D-20260812-003 至 007 涉及五个地域的大规模 state 归属；D-20260812-011/012 涉及核心合并语义与生成流程。它们可能有上游用户指令作为依据，但现有结构化证据只证明“主 agent 认为已获授权”，不证明按硬约束 1 完成了逐问、双轨描述和用户拍板。

`decision.schema.json` 只要求 `confirmed_by` 为任意非空字符串，所以自动闸门无法阻止 agent 自行写“confirmed”。应区分 `user_decision`、`derived_execution_record`、`bugfix_record`，只有第一类可授权重大设定/机制变化；否则当前“重大抉择必须提问”仍主要是软约束。

## 三、中等问题与潜在风险

### Windows handoff 路径修复不完整

`task_handoff` 仍以 `str(handoff_path.relative_to(ROOT))` 写回 tasks.json；机器 A 执行的 T-011 因而留下 `协作\\交接单\\T-011-g1.json`。Linux 上这是一个不存在的相对路径，但 `validate_tasks` 不检查 done 任务的 handoff 路径存在性，故校验仍通过。应改 `.as_posix()`，修正现存 T-011 字段并加 Windows 回归测试。

### 字段级合并会忽略第二份声明的来源路径/SHA

同一 state 在地域与经济文档中字段不相交时，`merge_override_documents` 只合并 PATCH_FIELDS；第二份声明的 `source_relative_path/source_sha256` 不与第一份比较，错误元数据会被静默丢弃。当前 65 个经济条目经独立抽查与快照一致，但程序化保证存在漏洞。合并时应强制 state_id、path、SHA 三元组完全一致，并增加对抗性测试。

### 466 个 BACKGROUND 州将保留原版 1936 归属

T-027 等任务把背景层定义为“不生成 override”；转换器对未声明 state 原样保留。因此完整生成后，这 466 州不会变成中立“某某地区”，而会继续携带原版 owner/controller/core 和可能的日期脚本。作为阶段性底稿可以接受，但不能把 T-028 的“可加载”误称为“世界地图内容完成”。当前仍会大量泄漏原版 1936 政权结构。

### 历史补登豁免范围过宽

D-20260811-012 已正确解决五个历史 commit 的全量复验问题；但 `historical_backfill` 没有限定门禁启用前的截止提交，也不检查 `confirmed_by=user`。任何后来提交都可以再增加精确 SHA 豁免，从而追认门禁启用后的违规 commit。建议固定 cutoff/allowlist policy，并只接受用户确认类型的决策。

### OpenCode filesystem MCP 权限绕过仍未修复

机器 B 已实测 `filesystem_write_file` 可绕过 execute/verify 的 `edit: deny`。D-20260811-012 延续“暂缓”，所以风险仍开放。Git/CI 可以阻止部分违规提交，但不能阻止工作区被越界改写。

### dry-run 证据不足且正式写入不是全目录事务

dry-run 目前只向终端打印计数和最多 10 个样例，没有生成结构化、可提交的统计报告；T-028 的“主调度器确认”难以审计。正式生成使用逐文件 `os.replace`，若中途 I/O 失败可能留下新旧混合目录，不是全目录原子切换。建议先生成到兄弟临时目录，完整复验后目录级替换/明确恢复；dry-run 输出 JSON 报告并绑定快照与 override 指纹。

### 快照的“province 全局完整性”表述偏强

当前能证明的是“state 文件中枚举到的 province 不重复且计数一致”，不能证明游戏 definition 中每个陆地 province 都出现在某个 state，因为导出器未消费全局 province 宇宙。文档中的“每个 province 恰好属于一个 state”应限定语义，或后续增加只读 definition/map 交叉验证。
