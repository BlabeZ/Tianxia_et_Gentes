# 任务书框架与意识形态系统详细分析

> 审查者：Codex（机器 C）
> 日期：2026-08-13
> 审查基线：`54f4ee295cd98a1b427bd80d811e39b13f0bd2b9`
> 范围：任务书 schema/状态机/活动任务，以及 T-043—T-046 意识形态、五轴坐标和运行时脚本
> 能力边界：机器 C `static_validation=true`、`load_test=false`，本报告不声称完成 HOI4 实机验证

## 总结

本轮更新已经把项目从“Markdown 任务清单”提升为有 schema、需求归属、租约代数、任务分支、输出白名单、失败计数、checkpoint、显式加载测试和权威测试报告的结构化工作流。意识形态系统的数据架构也已基本成形：4 个引擎极、8 个世界观身份、40 个唯一子类型、5 条政治轴、55 条国家政党坐标、1560 个有向距离对，当前默认坐标与静态四极归属一致。

但当前仍不能把意识形态系统称为“可玩闭环”。最严重的问题不是单个脚本语法，而是任务边界与目标互相冲突：T-045 按当前文件上限无法交付；T-046 已进入 `pending_test`，但好感网与八大旗标重建仍是未被调用/未实现的占位框架；而后续没有活动任务获准修改这些文件。另有原版 generic 子类型保留声明与实际文件不符、政治坐标 schema/校验缺口、本地化完全缺失等风险。

## 已确认的改进

### 任务书框架

1. `任务书/R-XXX-名称/T-XXX.json` 与 `需求/R-XXX.json` 建立明确归属；活动任务校验 spec ID、需求 ID、动态输入和归档状态。
2. `tasks.json` 成为生命周期唯一权威，任务台账由其确定性生成。
3. 任务分配绑定 48 小时租约、`lease_generation`、独立分支和能力快照；交接强制检查真实 branch tip。
4. `outputs` 已升级为任务书单一权威，并按文件/目录模式限制完整施工区间。
5. 加载测试由 `acceptance.requires_load_test` 显式驱动；权威 JSON/Markdown 报告绑定任务、代数、提交、机器、内容哈希并防重放。
6. 主调度器与 game-test 已有原子锁；当前统一校验和 147 项测试通过。

### 意识形态系统

1. B+ 分层清晰：五轴属性 → 8 大身份 → 40 子类型 → HOI4 四极兼容层。
2. 40 个唯一 subtype 的静态归属为 democratic 14 / communism 3 / neutrality 23 / fascism 0。
3. 40 个默认坐标均落在 -100—100，且当前全部通过五轴判据与静态四极归属对账。
4. 55 条国家政党坐标覆盖 17 个 tag，当前均继承 subtype 默认值，因此也全部与四极归属一致。
5. 距离表完整包含 40×39=1560 个有向对，统一校验会逐项重算五轴曼哈顿距离和 F 轴差。

## 发现

### H1：T-045 的交付在当前 `max_files` 下确定性不可达

T-045 要求为坐标表中的各国落地 `mod/history/countries/` 文件，并另交接一份 handoff。当前政党坐标涉及 17 个 tag，即便每个 tag 只生成一个国家文件，最低也是 18 个变更文件；任务书却设置 `max_files=8`。`task handoff` 对真实提交区间逐文件计数，超过即拒绝。

此外，T-045 的目标断言要求“validate 校验政党集合与坐标 JSON 绑定一致”，但 outputs 只允许 `mod/history/countries/` 和交接单，不允许修改 `scripts/workflow.py` 或 `tests/test_workflow.py`。现有验证器也没有解析国家历史文件完成这一断言。

**影响**：任务可以被机器 A 领取并开发，但按任务书完整实现后必然无法交接；如果为了通过上限只做少数国家，又违反目标断言。

### H2：T-046 被标为 `pending_test`，但核心运行时目标尚未实现

当前 `TXG_apply_opinion_band` 只会固定施加 `TXG_opinion_close`，没有按距离选择档位，且全仓库调用数为 0；注释提到的 `TXG_setup_opinions` 根本没有定义或调用。`on_startup` 只更新政体旗标，没有建立好感网。

`on_ruling_party_change` 只调用 `TXG_update_regime_type` 后清空八大政府旗标，没有重新设置任何一个 `TXG_gov_*`；全仓库 `set_country_flag = TXG_gov_*` 数量为 0。也没有重新计算或移除/重建好感网。国家五轴变量的生产者当前同样为 0，只是计划由 T-045 后续提供。

这与 T-046 任务书的“on_startup 按距离计算好感”“on_ruling_party_change 重算好感”“双钩子”“机器 A 开局好感验证”目标不一致。验证报告虽明确称其为框架，但状态已推进为 `pending_test`；当前 T-045 outputs 又不允许修改 T-046 脚本，T-048 outputs 也不含这些目录。

**影响**：实机测试最多能证明占位脚本能否加载，不能证明 T-046 的目标机制成立；即使测试失败，现有后续任务范围也无法自然补齐实现。

### H3：原版 generic 子类型“保留”的声明与实际文件不符

`00_ideologies.txt` 注释称 fascism generic 子类型保留，但 fascism 下没有 `types` 块；其他三极也只列项目自定义 subtype，没有原版 `conservatism/liberalism/socialism`、共产主义和中立/法西斯 generic subtype。该文件又明确作为同名覆盖文件使用。

项目仍保留大量原版 tag/历史输入，而 T-045 只计划覆盖当前坐标表涉及的 17 个 tag。若同名覆盖按预期替代原文件，未覆盖国家或角色对原版 subtype 的引用可能失效；至少“保留 generic”的验收事实目前不成立。

**影响**：可能造成国家领导人 subtype、历史政治数据或 UI 回退异常。该风险必须由机器 A 与当前本体 `00_ideologies.txt` 做受控 diff，并进行真实加载验证；静态解析器当前只识别自定义单行 subtype，无法证明兼容性。

### H4：T-045 把项目政党 ID 与 HOI4 `set_politics` 引擎槽混为一层

任务书写的是“`set_politics` 政党 key = `TXG_<TAG>_<party>`”。但项目自己的国家历史模板示例中，`set_politics.ruling_party` 和 `set_popularities` 使用的是引擎顶层 ideology 槽；B+ 架构也声明引擎只有 democratic/communism/fascism/neutrality 四极。当前没有定义 `TXG_*` 项目政党 ID 如何转换为：

- 引擎四极支持度；
- 执政党具体 subtype/领导人 subtype；
- 同一四极下多个现实政党的支持度和切换；
- 五轴变量与八大身份旗标。

**影响**：若直接把 `TXG_CHI_lixue` 写进 `ruling_party`，很可能不是合法的引擎顶层 ideology；若只写四极，又无法表达同一极下多个政党。T-045 开工前需要先把声明层 ID 到 HOI4 原生字段/脚本变量的转换契约写清楚，不能靠执行 agent 临场猜测。

### M1：政治坐标 schema 是“可选字段集合”，空对象也合法

`political-spectrum.schema.json` 顶层只要求 `schema_version`。实测 `{"schema_version": 1}`、空 `party_coordinates`、空 `default_coordinates` 均通过 schema。schema 没有用 `oneOf` 区分“默认坐标表”和“国家政党表”，也没有要求 decision/title/spectrum/thresholds 或至少一个坐标条目。

workflow 对默认坐标表有额外交叉校验，但国家政党表没有覆盖性下限；把国家政党表替换为空表仍可能通过其核心路径。

**影响**：数据大量丢失时 schema 不能独立 fail closed，验证安全依赖文件名和过程代码中的偶然补充。

### M2：国家政党坐标没有执行承诺的四极一致性校验

验证器只检查 party key 格式、country tag 前缀和 subtype 是否存在；不会把每条国家实际五轴坐标重新计算成四极并与 subtype 所属四极比较。隔离复现中，把 `TXG_CHI_lixue` 改为明显落入 fascism 的坐标后，`validate_political_spectrum` 仍返回零错误。

当前 55 条数据恰好全部等于 subtype 默认坐标，所以现状没有错配；但项目计划未来加入“国家修正”，一旦修正跨过四极阈值，双轨一致性会静默破坏。

### M3：任务书 v3 的失败控制字段在 schema 中仍非必填

README 把 limits、`revert_on_fail`、`checkpoint_policy` 描述为任务书运行契约，但 schema 的 required 列表不含这三项。缺失 limits 时运行时回退到部分默认值；缺失 `revert_on_fail` 时失败不回滚；缺失 checkpoint policy 时按自动推进处理。

当前 6 个活动任务都显式填写了这些字段，因此这是潜在框架风险而非当前数据错误。

### M4：验证通过后加载测试失败的 checkpoint 重试链可能不可交接

验证 PASS 会把 checkpoint 推进到任务 head。后续 load test FAIL 且 `revert_on_fail=true` 时，状态机会在该 checkpoint 上创建新 generation 分支，但不会创建对应的新原子 lease 提交，也不更新 base。后续 `task_output_base` 找不到匹配新 generation 的首个 lease subject，就会退回旧 base，把旧 lease 控制面和上代施工文件重新算入交接范围。

**影响**：T-043/T-046 若机器 A 测试失败，g2 修复可能因旧文件被计入 outputs/max_files 而无法交接。现有单测只断言“新分支被创建”，没有覆盖“回滚后修改→handoff 成功”的端到端路径。

### M5：本地化与显示配套为零，和“完整可玩传统 HOI4 mod”表述冲突

40 个自定义 subtype 在 `mod/localisation/` 中没有任何同名本地化键。项目参考文档明确要求 subtype 本地化、脚本显示、图标等配套；T-043 outputs 却不含 localisation/interface/gfx。

**影响**：即使脚本能加载，政治界面也可能显示原始 key 或缺少预期 subtype 视觉表达。此项可以后置，但不能把当前阶段描述为完整可玩成品。

### L1：审计记录存在 56/55 数量漂移

D-20260812-057、T-044 验证报告、00 卷修订记录和机器 A 简报都写“56 条国家政党坐标”；当前 JSON 实际为 55 条，且从提交内容看不是校验器生成的 56 条统计。

**影响**：不影响当前 schema 通过，但削弱决策记录与交付物数量证据的可信度，也会误导 T-045 文件规模评估。

### L2：意识形态数量文档仍同时保留“41 个、此前 40 作废”与“40 唯一 key”两种口径

实际情况是 02 卷存在 41 次名称出现，自由帝国主义跨自由主义/帝国主义重复，去重后为 40 个唯一 key。跨极表和代码采用 40；架构评估 9.8 仍写“实际清单 41、此前 40 表述作废”。

**影响**：未来 agent 可能再次扩成 41 个 key，重现已经解决的重复问题。应固定术语为“41 次分类出现 / 40 个唯一 subtype key”。

## 建议修复顺序

1. 立即冻结 T-043/T-046 的 PASS 登记和 T-045 分配，先建立一个明确的意识形态闭环修复任务。
2. 修订 T-045：按 tag 拆分或把 `max_files` 提升至实际规模；把校验器、测试、坐标/旗标生成器纳入 outputs；先拍板项目政党 ID 到 HOI4 四极/subtype/变量的转换契约。
3. 将 T-046 从“待纯加载测试”退回可开发状态或建立续作任务，补齐好感网生成、清除/重建、八大旗标重建和轴变量生命周期；再进行实机验收。
4. 在机器 A 对当前本体 ideology 文件做只读受控差异审查，补齐 generic subtype 与版本相关顶层字段，再测试 17 个覆盖 tag 和至少一个未覆盖原版 tag。
5. 加固 political-spectrum schema 与 validator：区分两种文档形态、要求非空集合、校验国家实际坐标→四极、校验 tag 覆盖和历史文件绑定。
6. 修复 checkpoint 重试的 g2 原子 lease/输出基线语义，并增加“validation PASS→load FAIL→g2 handoff”的集成测试。
7. 单独登记本地化/显示配套任务，统一 55/56 和 41/40 文档口径。

## 总体评级

- 任务书框架设计成熟度：**中高**；安全边界明显加强，但失败重试链和 schema 强制性仍需补洞。
- 意识形态数据层成熟度：**中高**；静态结构完整且当前数据自洽。
- 意识形态运行时成熟度：**低—中**；目前是可审查框架，不是已闭环机制。
- 当前实机交付可信度：**不足**；T-043/T-046 必须在修复任务边界后由机器 A 完成真实加载和行为验证。
