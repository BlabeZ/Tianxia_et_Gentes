# 当前开发框架／流程审查（Codex，2026-08-13）

## 结论

当前框架的静态门禁、任务租约、提交区间校验、设定修订记录和本体只读边界整体设计扎实；仓库级 `validate` 与 137 项单元测试均通过。但框架尚不能安全完成真实加载测试闭环，且存在 3 个高风险确定性问题、4 个中风险流程漂移／并发风险。当前不应把自动加载测试能力视为可用，也不应仅凭现有 `task test-result` 将 `pending_test` 任务推进到 `ready_to_merge`。

## 审查范围与证据

- 已读取：`AGENTS.md`、`协作/README.md`、`协作/tasks.json`、`协作/决策协议.md`、任务书、决策记录、交接单、hooks、CI、schemas 与核心脚本。
- 环境：机器 C，`partial`；`snapshot_export=false`、`load_test=false`，因此未接触游戏本体，未做实机加载测试。
- 已执行：`python3 scripts/workflow.py env-check --publish`、`git pull --ff-only`、`python3 scripts/workflow.py validate`、`python3 -m unittest discover -s tests -v`、`git diff --check`、`python3 -m compileall -q scripts tests`。
- 结果：仓库校验通过；137 项测试通过；工作树在写本报告前干净，`main` 与 `origin/main` 同步。

## 高风险发现

### H1：`game-test` 的 `load_test` 能力门禁恒为 false，真实命令不可达

`scripts/workflow.py:3739-3743` 在 `game_test_preflight_errors()` 中调用 `derive_environment(..., probe_external=False)`；而 `derive_environment()` 只有在 `probe_external=True` 时才构造并检查 `game_path` 与 `user_docs_path`（`scripts/workflow.py:1144-1151,1187-1201`）。因此即使机器 A 已发布 `load_test=true`，`game-test` 命令本次重新派生出的 `load_test` 仍恒为 false，并报“本机不具备 load_test 能力”。

影响：Gate 0 完成后仍无法进入实机启动路径；现有 mock 测试通过是因为测试直接 mock 了 `derive_environment()` 返回值，没有覆盖真实参数组合。

建议：主代理专用 `game-test` 应像 `state-build` 一样在固定入口使用 `probe_external=True`，同时验证本机 freshly-published 环境快照与实时派生结果一致；新增不 mock `derive_environment()` 的临时目录集成测试。

### H2：`task test-result` 不消费权威 JSON，可用任意 Markdown 报告推进状态

`checked_report_path()`（`scripts/workflow.py:1977-1989`）只验证路径在 `协作/审查记录/` 且文件存在；`task_test_result()`（`scripts/workflow.py:2202-2228`）随后只信任命令行 `--result pass|fail`，没有校验自动测试 JSON 的 `task_id`、`generation`、`git_head`、`runner_commit`、`mod_tree_sha256`、`profile`、`verdict`、`registrable`、session 是否已消费，也没有验证测试机器 `load_test=true`。

这与 `docs/加载测试自动化规划.md:289-291` 和归档 T-042 任务书中的强制要求直接冲突。当前任意存在的 Markdown（甚至 fixture 的 `INCONCLUSIVE` 报告）在路径层面都可被拿来配合 `--result pass`，把任务推进到 `ready_to_merge`。

建议：在修复前暂停登记 T-043、T-046 及后续任务的 test PASS。将 `test-result` 改为只接受同名权威 JSON，并强制机器校验上述绑定字段、`verdict==PASS`、`registrable==true`、未消费；登记成功后原子写入 `consumed_by`。FAIL 也必须确认是可归因 FAIL，INCONCLUSIVE 不得消耗失败次数。

### H3：T-042 被提前置为 `done`，任务定义与实际交付不一致

归档任务书 T-042 的目标包括真实“启动→readiness→受控退出→日志解析”、Gate 0、`process-smoke/menu-debug/map-load` 各 3 次稳定运行和 T-028 端到端；但当前实现 `game_test_command()` 只调用 preflight-only，并在所有路径返回 `INCONCLUSIVE`（`scripts/workflow.py:3792-3813`）。决策 D-20260812-068、验证报告和规划文档也明确 Phase 3/4 尚未完成。尽管如此，T-042 已于提交 `23bcc42` 归档并标记 `done`。

根因之一是 T-042 的 `acceptance` 未设置 `requires_load_test=true`，任务登记的 `required_capabilities` 也不含 `load_test`；静态验证 PASS 后状态机直接进入 `ready_to_merge`。

影响：状态权威宣称自动加载测试闭环已完成，但实际只有 Phase 1+2；下游可能错误依赖一个尚不可用的执行器。

建议：不要改写历史证据；由主代理新建明确的续作任务（或按既定协议重新打开并增代）承接 Gate 0、Phase 3/4、H1/H2 修复和实机验收，T-028 在该任务完成前保持不可测试。

## 中风险发现

### M1：加载测试要求是可选布尔值，文字验收不会触发门禁

任务书 schema 只要求 `acceptance.load_test` 是非空字符串，`requires_load_test` 却是可选字段；状态机仅识别后者（`scripts/workflow.py:2171-2178,2948-2954`）。T-043、T-046 都写明“机器 A 实机加载”，但未设置 `requires_load_test=true`，任务能力也不含 `load_test`；它们当前进入 `pending_test` 依赖主代理手工传 `--requires-load-test`，操作员漏传即可跳过实机门禁。

建议：对活动任务采用结构化验收枚举或令 `requires_load_test` 必填；至少在 `load_test` 文本不是明确“不适用”时拒绝缺少布尔声明。不要靠自然语言推断最终状态，但应强迫任务作者显式选择。

### M2：单一主调度器没有仓库级互斥锁，原子操作仍可并发竞争

框架声明“同一任务链只有一个主调度器”，但 assign/handoff/validation/test/complete 只做分支和 clean-worktree 检查，没有持有跨进程锁。审查过程中共享工作区确实被另一主流程从任务分支切到 `main` 并完成合并，证明并发访问在现实中会发生。两个主流程若同时通过 preflight，仍可能在 `git add/commit/branch` 多步序列间相互干扰。

建议：为所有主调度生命周期命令增加原子创建的 coordinator lock（含 PID、host/machine_id、启动时间与操作名），异常退出后只报告 stale lock、由主代理显式清理；锁应覆盖整个检查—写文件—暂存—提交—建分支序列。游戏测试另有 `GAME_TEST_LOCK_PATH` 常量，但目前也未实现锁行为。

### M3：`tasks.json.outputs` 与任务书／真实交接持续漂移，校验器未交叉验证

示例：T-043 的任务登记包含 `common/scripted_effects/`（缺 `mod/`），而任务书与交接为 `mod/common/scripted_effects/`；T-046 的任务登记只列一个输出目录，但任务书和交接覆盖多个 mod、脚本、数据与决策文件；T-042 的登记输出也少于归档任务书实际输出。当前 `validate` 分别验证 schema，却不要求 registry outputs 与活动任务书 outputs 一致。

影响：台账、人类审查和任何读取 registry outputs 的调度逻辑看到的范围不可靠；虽然 handoff v2 当前主要用任务书 scope，双权威漂移会逐步积累。

建议：明确唯一输出权威。推荐以任务书 `outputs` 为权威并由任务分配时同步派生 registry 值；`validate` 对活动任务做完全一致校验，历史归档只报告兼容性警告。

### M4：Phase 3 尚有安全占位符，不能直接“补上 subprocess”后启用

`game_test.executable_path` 当前只检查非空，没有检查文件存在、是否等于受信 game_path 下已探测的 HOI4 可执行文件、或是否与报告哈希绑定；报告路径检查在 preflight 中使用字符串 `startswith()`，未复用 `checked_report_path()` 的 resolve/relative_to 边界；`GAME_TEST_LOCK_PATH` 尚未使用。若直接在现有薄入口后加入进程启动，可能启动任意本机可执行文件、越界写报告或并发运行。

建议：Phase 3 启用前先把可执行文件解析限制为受控候选、校验 descriptor 与 mod 树绑定、复用规范化报告路径函数，并实现 Job Object/PID 创建时间核对、会话锁及原子报告写入。

## 已确认有效的部分

- `env-check --publish` 能按本机实测降级能力；机器 C 没有本体导出／加载能力时保持默认拒绝。
- 本体、Workshop 与用户目录没有被本次审查读写；state 快照与转换边界清晰。
- 任务租约 generation、任务分支 tip、交接区间、scope/max_files、待定项消失授权、设定修订记录同 commit 等已有较完整的校验和单测。
- pre-commit、pre-push 与 GitHub Actions 共用统一验证器，并覆盖 Linux/Windows；本机 `core.hooksPath=.githooks`。
- 仓库当前静态一致性通过。但 GitHub main ruleset/保护是否 Active、必需检查是否真正不可绕过，无法仅靠仓库内容确认，仍需仓库管理员在远端实测。

## 建议处置顺序

1. 立即冻结 `task test-result --result pass` 的实际使用，避免 pending_test 被错误放行。
2. 建立 T-042 后续修复任务：先补 H1、H2 和 M1，再做 Gate 0 与 Phase 3/4。
3. 实现主调度器互斥锁，并补并发进程测试。
4. 收敛 tasks/spec outputs 双权威并修复活动任务漂移。
5. 机器 A 完成 Gate 0 拍板和真实基线后，按顺序做 process-smoke → menu-debug → map-load，各 3 轮；最后跑 T-028 端到端。

## 再次复核（2026-08-13）

本节按用户要求对上述结论做第二次可复现性检验。所有会改变任务状态的命令均在 `/tmp` 隔离 Git 副本执行，未修改主仓库任务状态或游戏／模组内容。

### 已实际复现

1. **H1 确认存在**：在隔离副本构造有效的 game path、HOI4 候选可执行文件、user docs 与 current 快照。同一配置调用 `derive_environment(..., probe_external=True)` 得到 `load_test=true`；调用当前 preflight 所用的 `probe_external=False` 得到 `load_test=false`。实际运行 `game-test` 随即输出“本机不具备 load_test 能力”。因此这是确定性不可达 bug，不是机器 C 环境误报。
2. **H2 确认存在且可实际放行**：在隔离副本提交一份明确声明“不是加载测试报告”、不含 JSON/verdict/profile/registrable 的普通 Markdown；调用 `task test-result --id T-043 --generation 1 --result pass --report <该普通文件>` 后，命令成功提交状态，T-043 从 `pending_test` 变为 `ready_to_merge`。证明任意审查目录 Markdown 可绕过权威测试报告要求。
3. **M1 确认存在且可实际跳过加载测试**：在隔离副本将 T-043 回放到 `pending_validation`，调用 validation PASS 且不传 `--requires-load-test`。尽管任务书 `acceptance.load_test` 明写“机器A实机加载无意识形态错误”，因 `requires_load_test` 缺失，状态直接变为 `ready_to_merge`。

### 由当前权威文件直接确认

1. **H3 确认存在**：`tasks.json` 仍将 T-042 标为 `done`；归档任务书仍要求三类 profile 各 3 轮和 T-028 端到端；代码仍是 preflight-only、始终返回 INCONCLUSIVE；决策、规划和验证报告仍明确 Phase 3/4 待机器 A。四方证据互相印证，完成状态与实际交付不一致。
2. **M3 确认存在**：T-042、T-043、T-046 的 registry outputs 均与任务书 outputs 不一致；其中 T-043 还存在 `common/scripted_effects/` 缺少 `mod/` 的路径错误。

### 结构性／条件性风险（未冒充既成损坏）

1. **M2 保持为结构性风险**：代码中没有 coordinator lock；`GAME_TEST_LOCK_PATH` 也只有常量和规划文字，没有加锁实现。本次未并发执行两个生命周期写操作，因此没有声称已复现仓库损坏。
2. **M4 保持为条件性风险**：修正 mock 夹具后，当前 preflight 接受 `协作/审查记录/../tasks.json` 形式的路径，也接受未绑定受信 game path 的任意 executable path，错误列表为空。但当前 Phase 3 尚不启动进程、不写报告，所以这是启用实机执行前必须修复的可达校验缺口，暂不是已发生的外部执行／覆盖事件。

### 复核后的总判定

原报告核心结论成立，并获得更强证据：H1、H2、M1 是可稳定复现的确定性漏洞；H3、M3 是当前状态中的确定性一致性错误；M2、M4 是真实存在但危害尚需并发或 Phase 3 启用条件的风险。现阶段继续冻结 `task test-result --result pass` 仍属必要措施。
