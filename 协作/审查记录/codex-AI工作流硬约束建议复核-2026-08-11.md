# AI 工作流硬约束建议复核

日期：2026-08-11

## 结论

建议指出了真实漏洞，但原计划不能原样实施。应先确认并启用远端保护，再增加“待定项解决”的结构化语义门禁；本地 Git hooks 适合作为快速反馈层，OpenCode plugin 暂不列为必要项。

## 事实核实

| 报告说法 | 核实结论 |
|---|---|
| `.github/workflows/workflow-integrity.yml` 是唯一入库 CI 工作流 | 正确。它在 PR 与 main push 上运行单元测试、全库校验及提交范围校验。 |
| CI 是“无法绕过”的最后闸门 | 不成立。push 事件发生在远端已接受提交之后；只有 main 分支保护或 ruleset 强制 PR、必需状态检查、禁直接/强推且限制 bypass 时，失败检查才构成合并闸门。远端保护状态本次无法通过未认证 API 确认。 |
| 本地 Git hooks 未启用 | 机器 C 上正确：`.git/hooks` 只有 sample，且未配置 `core.hooksPath`。 |
| 项目未使用 OpenCode plugin | 正确：项目不存在 `.opencode/plugins/`，项目级 `.opencode/opencode.json` 不存在且被忽略。 |
| 全局 OpenCode 配置不存在 | 错误。机器 C 存在 `~/.config/opencode/opencode.jsonc`；其中本次未发现 plugin 配置。 |
| verify 无 Git 权限，因此不能验证提交区间 | 表述不准确。verify 禁止任意 Git 命令，但被允许调用 `workflow.py validate --base ... --head ...`，校验器可在受控入口内部读取 Git 区间。真正缺口是校验器没有待定标记消失规则。 |
| “待定/待确认”静默填实是最大剩余漏洞 | 基本正确。当前只保证任何设定层 commit 同时有决策 JSON 和 00 卷修订行；并不证明该决策明确授权了某个待定项的解决。 |

## 对建议计划的修订

### 1. 远端强制规则应升为最高优先级

确认或配置 main ruleset／分支保护：必须通过 `workflow-integrity / validate`、必须走 PR、禁止强推、限制直接 push，并审查 bypass 列表。否则 Actions 只能事后报警，不能阻止 main 被写入。

### 2. 待定项门禁需要“语义对应”，不能只看是否存在决策文件

当前任何 `Settings/` 或 `设定书/` 改动已经必须同 commit 更新结构化决策 JSON，所以“标注消失且没有任意决策 JSON”大部分是重复检查。

建议逐 commit 检测 `待定/待确认/【拟定】/【待推演】` 等受控标记的净消失，并要求同 commit 的决策记录包含机器可读的解决声明，例如 `resolved_pending`，至少绑定相对路径、原标记指纹和解决摘要。只用 `affected_files` 目录匹配不足以证明用户批准了具体填实。

检测应处理移动、重命名和同 commit 搬迁，避免把“标记换位置”误判为解决；同时加入无决策删除、泛化决策、跨 commit 补决策、文件重命名、合法解决等对抗测试。

### 3. Git hooks 值得加入，但属于可绕过的本地反馈层

- `pre-commit` 不能只运行现有无参数 `validate`，因为它看不到尚未形成的“当前 commit”边界。应先实现 `validate --staged`，从 Git index 核对同 commit 义务。
- 当前测试入口是 `python -m unittest discover -s tests -v`，不是 pytest。
- `pre-push` 应读取 Git 提供的 stdin ref/SHA，并调用 `validate --base <remote_sha> --head <local_sha>`；当前 CLI 不接受 `--base origin/main..HEAD` 这种单参数范围。
- hook 脚本需兼容 Windows 的 `py -3` 与 Linux 的 `python3`。
- `core.hooksPath` 需要每机启用且可被 `--no-verify` 绕过，因此文档中应称“快速反馈／纵深防御”，不能称不可绕过硬闸门。

### 4. OpenCode plugin 暂列可选

本机安装的 OpenCode plugin API 确实提供 `tool.execute.before`，技术上可以拦截工具参数。但它只覆盖 OpenCode，且单纯字符串匹配无法可靠处理环境变量、符号链接、PowerShell、间接 Python 调用等路径变体，容易产生虚假安全感。

在现有 subagent 默认拒绝、固定只读导出器和各工具沙箱之外，若仍需保护主 agent，优先考虑操作系统只读 ACL／挂载。只有明确机器 A 的威胁模型和 OpenCode 主 agent 实际权限后，再决定是否维护 plugin。

## 建议优先级

1. P0：核实并启用 GitHub main ruleset／分支保护。
2. P1：设计结构化 `resolved_pending` 门禁及对抗测试。
3. P1：增加跨平台 `.githooks/`，同时实现 `validate --staged` 和正确的 pre-push ref 解析。
4. P2：按机器 A 的实际权限决定是否增加 OpenCode plugin；不作为前三项的替代品。
