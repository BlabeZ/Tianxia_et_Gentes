# 重大决策协议（跨工具中立规范）

本文件是 OpenCode、Codex、Claude Code 共同遵守的唯一决策流程来源。工具专用 skill/command 只能引用本文件，不得复制出另一套规则。

## 触发条件

影响世界观、游戏机制、内容方向、工作流、权限边界或文件结构的选择，必须暂停执行并由主 agent 一次一问。subagent 不得拍板，只能把决策点退回主 agent。

需求含义、边界或成功标准不明确时，也必须一次一问澄清，直到主 agent 对用户真实意图达到约 95% 置信度。

## 双轨中文

每个重大问题使用两条中文表达轨道：

1. **正式表述**：准确说明技术或设定含义；
2. **通俗解释**：说明选择后实际会发生什么、成本和风险是什么。

不要求中英双语。简单机械问题不必重复两遍。

## 两类流程共同规则

- 一次只问一个问题，等待回答后再进入下一分支；
- 能从项目文件或工具中查明的事实不得反问用户；
- 不得在用户确认意图或重大决定前输出正式 spec、计划或开始实现；
- 只适用于有实时用户响应的交互场景；CI、定时任务或无人值守循环遇到信息不足时必须报告阻塞，不得猜测。

## 重大决策每次提问

- 提供 2—4 个互斥且覆盖合理空间的选项；
- 每个选项同时说明优点、缺点和实际影响；
- 明确标记推荐项并说明推荐原因；
- 工具有选项框/question tool 时必须使用；不可用时采用同结构的纯文本回退。

## 模糊需求附加规则

以下流程用于需求缺少使用者、为何现在、成功标准或约束，或用户只提出“现代、可扩展、最佳实践”等惯例性目标的情况。明确、自包含的信息查询与机械操作不触发本流程；用户明确要求速度优先于访谈时，也不强制展开。

### 1. 首次声明假设与置信度

第一次澄清前，主 agent 必须用一句话声明对用户真实目标的**当前假设**，并给出可辩护的 `0—100%` 置信度。置信度低于约 `70%` 时，必须同一处说明尚缺哪些信息；不得只报一个没有依据的数字。

### 2. 一次一问，每问附当前猜测

每一个后续问题都必须是一个聚焦问题，并同时附上主 agent 对答案的**当前猜测及其理由**。等待用户纠正后再更新假设、置信度和下一问。需求访谈默认使用可自由纠正的问法，不得为了省事批量抛出问题；只有当用户已明确目标、正在选择具体权衡时，才转入上节的互斥选项流程。

### 3. 区分真正想要与“应该想要”

若回答只诉诸“可扩展、现代、稳健、干净架构、最佳实践、标准做法”等应然性或惯例性表达，却没有可检验结果，必须追问：**“如果不需要向任何人证明这个选择，你真正想要什么？”** 不得把彰显专业度的词语直接当作成功标准。

### 4. 约 95% 停止检查

只有当主 agent 能回答“**我能否预测用户对接下来三个问题的反应？**”为“能”时，才视为达到约 `95%` 的共享理解并停止追问；这不是凭感觉填写的置信度。若连续多轮后仍不能预测，必须明确说明基础信息仍然缺失，询问是否退一步重新界定问题，不得无限盘问或自行补全。

### 5. 六字段重述

停止追问后，使用用户自己的措辞按以下六项逐行重述，并允许逐项纠正：

- **目标**：最终要改变或得到什么；
- **使用者**：谁实际使用或受益；
- **为何现在（Why now）**：什么变化使这件事现在需要做；
- **成功标准**：如何判断已经有效；
- **约束**：真正不可突破的限制；
- **不包含（Out of scope）**：明确不做什么。

“不包含”不得省略。多会话项目只有在用户确认后才可另行保存意图文档。

### 6. 明确确认门槛

终态必须是用户对六字段重述作出的明确确认。以下弱确认**不算终态确认**：

- `whatever you think`、 “你看着办”或“听你的”：这是委托，不是用户确认；改用两个具体取舍继续澄清；
- `sounds good` 或“听起来不错”：追问是否有任何一项需要修订；
- `sure, let's go`、礼貌性的“行，开始吧”：确认这是对重述本身的认可，而非退出访谈；
- 沉默后直接要求开工：询问是否遗漏了关键内容。

用户纠正任何一项后，必须合并修订并重新完成六字段重述，直到得到明确确认。确认后的 spec、计划和任务必须以这份确认意图为输入，而不是回到最初的模糊请求。

## 决策落盘

决策树完成后生成：

- `协作/决策记录/D-YYYYMMDD-NNN.json`：机器可读权威记录；
- 同名 `.md`：正式表述与通俗解释摘要。

相关任务、交接、提交和设定书修订记录必须引用 `decision_id`。
