# 《天下与万邦》多 agent 协作框架

> 决策依据：`D-20260810-001`。运行细则以 `AGENTS.md`、`协作/README.md`、`协作/tasks.json` 和统一校验器为准。

## 一、设计目标

框架服务于 OpenCode、Codex、Claude Code 和 subagent 的跨机器协作，解决五类问题：

1. 不共享会话上下文时，如何共享可靠 Memory；
2. 如何让调度器依据真实能力分配任务；
3. 如何保证游戏本体绝对不被 agent 修改；
4. 如何阻止过期 agent 或不完整交接进入主线；
5. 如何让重大拍板跨工具、跨会话可追溯。

正式架构：文件化共享状态 + 单一主调度器 + 受控本体快照 + 带 fencing token 的任务租约 + 本地/CI 同源校验。

通俗解释：所有工具看同一套“任务账本、能力卡、决定档案和扫描资料”；只有一个调度者发任务；游戏文件不交给 agent；过期通行证不能交作业；违规修改进不了主线。

## 二、角色与权限

| 角色 | 职责 | 可写范围 | 禁止事项 |
| --- | --- | --- | --- |
| 主调度器 | 环境发布、任务分配、租约、分支、交接、合并 | 协作状态与任务范围内文件 | 不得绕过用户拍板或统一校验 |
| snapshot-export | 固定脚本只读提取本体元数据 | `协作/扫描快照/` | 不复制原文，不写游戏目录 |
| scan subagent | 快照+设定卷→归属映射 | 扫描产出、当前会话摘要 | 不访问本体、不执行Git、不改任务状态 |
| execute subagent | 按地域生成声明式 state 改写清单 | `协作/state-overrides/`、当前交接证据和会话摘要 | 不写完整state正文、不访问本体、不执行Git |
| state-build | 主 agent 受控读取本体并生成完整states | `mod/history/states/` | 快照非current、SHA不符或清单歧义时必须拒绝 |
| verify subagent | 对 base..head 做阶段验证 | 当前验证报告 | 不修代码、不改任务状态、不执行Git |
| Codex / Claude Code | review、debug、方案审查 | 各自审查记录或主调度器明确授权范围 | 不使用工具私有记忆替代共享状态 |

OpenCode agent 的具体硬边界位于 `.opencode/agent/*.md`。scan/verify 不再允许 `git *`，execute 不再使用工作区默认写权限。

## 三、Memory 模型

### 3.1 权威来源

- 世界观原文：`Settings/`；
- 汇总设定：`设定书/`；
- 任务状态：`协作/tasks.json`；
- 用户拍板：`协作/决策记录/`；
- 机器能力：`协作/环境/<machine_id>.json`；
- 本体结构输入：`协作/扫描快照/states.json`；
- state 改写权威数据：`协作/state-overrides/*.json`；
- 任务提交证据：`协作/交接单/`；
- 长程恢复：`协作/会话记录/`。

Markdown 台账和快照摘要都是派生视图，不是第二份权威数据。

### 3.2 本地私有状态

`.opencode/local.json`只保存机器 ID、操作系统和三个本地路径，且被 gitignore。能力由统一脚本派生，不能在配置中自行声明。`.opencode/opencode.json`同样被忽略，防止外部目录权限和路径泄漏。

## 四、环境识别

统一入口：

```text
python3 scripts/workflow.py env-check --publish
```

以上示例使用 POSIX 命令；Windows 把 `python3` 替换为 `py -3`。

主 agent 的 `--publish` 模式验证配置类型、states 目录、已提交快照、本体指纹、用户目录和可执行程序，然后输出五项能力与总体档位。subagent 的不发布模式只检查仓库内状态，不探测外部路径。输出到 Git 的环境快照不含绝对路径。

任务只按 `required_capabilities` 调度：例如快照导出要求 `snapshot_export`，light 机仍可承担只要求 `static_validation` 的验证工作。正式分配时，负责人快照还必须在分配时刻前 15 分钟内生成且不得来自未来。

## 五、本体只读链路

```text
game_path/history/states（主 agent 固定脚本只读）
                 ↓
协作/扫描快照/states.json（元数据、SHA、版本、指纹）
                 ↓
scan / execute / verify subagent（只读快照；execute只写声明式清单）
                 ↓
主 agent state-build（核对实时指纹与逐文件SHA）
                 ↓
mod/history/states（完整覆盖文件）
```

full 机不再为所有 agent 配置全局 `<game_path>/** external_directory allow`。如宿主工具运行脚本需要目录授权，只给主 agent 的固定 `snapshot-export` 和 `state-build` 操作，不能给 execute subagent。

`state-build` 采用 `D-20260811-004` 的受控直转方案：改写清单绑定总体快照指纹、来源相对路径与单文件 SHA；转换器保留未声明内容，只修改 Schema 支持字段。它拒绝重复唯一字段、路径越界、旧快照、同州多清单冲突和单行歧义结构。真实本体正文不会进入快照或 subagent 上下文。

仓库 diff 无法证明外部游戏目录没被修改，因此验证清单不再作这种错误推断。安全边界由“不授予访问能力”实现。

## 六、任务状态机

状态：`todo / in_progress / pending_validation / pending_test / ready_to_merge / decision_required / done / blocked / stale`。

只有主调度器调用：

```text
python3 scripts/workflow.py task assign ...
python3 scripts/workflow.py task heartbeat ...
python3 scripts/workflow.py task reclaim-stale
python3 scripts/workflow.py task handoff ...
python3 scripts/workflow.py task validation-result ...
python3 scripts/workflow.py task test-result ...
python3 scripts/workflow.py task complete ...
```

分配时固定 `base_commit`，使用分支 `task/<task_id>-g<generation>`，并启动48小时租约。`task assign` 只容许目标机器环境快照作为 `main` 上的额外未提交变更；它将该快照（如已变更）、`tasks.json` 和派生台账原子提交，校验暂存区不含其他文件，再从该提交创建本地任务分支。命令不自动推送；交接 head 必须是该分支实际 tip。自动回收会递增 generation；任何旧 generation 的心跳或交接直接失败，这就是 fencing token。

旧版“各机器先提交台账锁再 push”的协议已废止。它在 push 竞争失败后会产生分叉，使 `pull --ff-only` 无法恢复，也无法明确锁提交究竟位于 main 还是任务分支。

## 七、Workflow

```text
阶段A  mod工程骨架
  ↓
阶段B-0a  full/partial机显式导出受控states快照
  ↓
阶段B-0b  scan消费快照+设定卷，生成归属映射
  ↓
阶段B-0c  受控转换器、Schema与静态门禁
  ↓
阶段B  按11卷既有地域拆分任务分支，并行生成state改写清单
  ↓ 每任务
结构化交接(base/head/generation/decision_ids)
  ↓
verify检查完整提交区间
  ↓
T-028由full/partial机汇总清单，受控生成全部完整states
  ↓
静态通过 → 需要加载则待测试 → 待合并
  → 主调度器显式合并 → complete验head已进main → 完成
```

按洲任务已在 `tasks.json` 明确拆为东亚、东南亚与南亚、中亚与西亚、欧洲、非洲、北美、拉丁美洲、大洋洲与太平洋。它们只产出 `协作/state-overrides/*.json`；T-028 才写 `mod/history/states/`。北美任务显式依赖尚待用户拍板的界线任务。

## 八、验证与 CI

统一命令：

```text
python3 scripts/workflow.py validate
```

GitHub Actions 在 push/PR 运行同一入口，并对 base..head 中的每个 commit 增加变更规则：

- 设定层改动必须在同一 commit 新增00卷修订记录行，并引用同 commit 内与变更路径匹配的 `decision_id`；
- 协作核心规则改动必须在同一 commit 关联 `affected_files` 真实匹配的决策记录；
- 已提交 JSON Schema 由 Python 标准库门禁直接执行，不是仅供阅读的文档；
- Markdown 台账必须与 `tasks.json`完全一致；
- 权限配置不得重新引入 `git *` 或 execute 默认可写；
- 环境快照不得包含本机绝对路径；
- 交接单代数必须与当前任务一致；
- tag 数量固定校验为复用25+新建13=38。

验证报告仍落入 `协作/审查记录/`。CI 是硬闸门，人工 review 是语义闸门，两者不能互相替代。

## 九、重大决策

跨工具唯一协议为 `协作/决策协议.md`。OpenCode 使用 namespaced 的 `teg-grill-me/teg-interview-me` 适配器，避免被同名全局 skill 覆盖；Codex 和 Claude Code 直接读取中立协议。

所有重大问题使用“正式技术表述 + 通俗解释”双轨中文，一次一问并明确推荐。拍板形成 `decision_id` 后才可进入任务。

模糊需求按 `D-20260811-005` 执行完整 interview 收束：逐问必须暴露当前猜测，应然性词语不能代替实际目标；终态重述必须包含“为何现在”和“不包含”，并通过三问预测检查及用户明确确认。弱确认不是拍板。统一校验器对这些协议锚点和 namespaced 短适配器执行静态检查，防止规则再次被静默简化。

## 十、多机同步边界

Git 同步：mod、设定、任务、决策、脱敏环境快照、本体元数据快照、交接和审查记录。

不通过 Git 同步：绝对路径、凭据、OpenCode/Claude/Codex 私有会话数据库、游戏本体原文、用户文档内容。

主调度器根据 `协作/环境/*.json`选择机器，但每次正式分配前仍需在目标机器重新运行 `env-check --publish`。跨机分配必须先同步该脱敏快照；不得手填 `checked_at` 或能力布尔值绕过实测。
