# 加载测试自动化规划：游戏自动化测试执行器

> 任务：T-042｜需求：R-005｜决策：D-20260812-022
> 状态：详细设计完成，实施前门禁未解除；本文件记录后续实现的唯一技术基线。

## 一、目标与成功边界

在机器 A（Windows、full）建立可审计的自动化测试闭环：

`前置校验 → 选择受控测试配置 → 启动 HOI4 → 确认 mod 已加载 → 等待目标阶段 → 保持运行 → 受控退出 → 读取本次新增日志 → 判定 → 生成 JSON + Markdown 证据`

执行器服务于 `requires_load_test=true` 的任务（首先是 T-028），测试证据交给现有 `task test-result` 状态机消费。

### v1 必须做到

1. 直接启动游戏可执行文件，不经过 launcher；
2. 使用已验证的启动参数加载指定 mod，并默认启用 debug；
3. 证明进程存活、mod 已加载且到达测试配置定义的 readiness 阶段；
4. 只解析本次运行追加的日志，不能把历史错误算入本次结果；
5. 只终止本次启动的进程树；
6. 输出机器可读 JSON 和人类可读 Markdown 报告；
7. PASS/FAIL/INCONCLUSIVE 三种结论明确分离。

### v1 不承诺

- 不通过鼠标键盘 UI 自动化选择国家或点击“开始游戏”；
- 不自动运行完整战役、国策或事件时间线；
- 不根据“进程活着一段时间”单独判定 PASS；
- 不自动调用 `task test-result` 修改任务状态（主调度器仍显式登记）；
- 不修改游戏本体、Workshop 模组或用户配置文件。

“进入游戏”在 v1 中定义为**到达经机器 A 实测确认的 readiness 标志**。主菜单加载与剧本/存档加载是两个不同测试配置，不得混称。

## 二、实施前硬门禁（未解决前 T-042 不得 assign）

### 门禁 A：用户目录只读策略与游戏写日志的冲突

项目规则将 `user_docs_path` 视为只读参考；但启动 HOI4 会由**游戏进程自身**写入 `logs/`、缓存及可能的设置文件。即使 agent 只读日志，启动行为也会间接触发写入。

实施前必须由用户拍板以下策略之一：

1. **受控例外（推荐）**：agent 不直接写用户目录；允许其启动的 HOI4 进程在一次测试会话内写**经 Gate 0 实测形成的路径级 allowlist**。执行前后递归快照用户目录（相对路径、类型、大小、mtime），报告新增/修改/删除集合；allowlist 外写入阻断 PASS 并判 INCONCLUSIVE；执行器只读日志增量，不删改日志；
2. 用户提供隔离测试用户目录，并确认官方/实测启动参数可将所有运行时写入导向该目录；
3. 保持绝对只读，则无法实现自动启动游戏，只能保留人工加载测试。

### 门禁 B：ASCII mod 路径与当前工作区 Unicode 路径

项目位于含中文字符的路径。项目文档已记录 HOI4 本地 mod 路径含非 ASCII 字符可能导致加载失败。执行器不能假定 `repo/mod/descriptor.mod` 可被游戏可靠读取。

推荐方案：用户在机器 A 预先提供一个**只读、ASCII 绝对路径**，指向当前仓库 `mod/` 的 junction/symlink 或受控镜像；执行器仅验证并使用，不创建、不更新外部映射。配置键为 `game_test.mod_descriptor_path`。

若最终选择复制到 ASCII staging 目录，必须另行授权外部写入边界、清理策略和内容指纹校验，不能在实现时临时决定。

### 门禁 C：真实启动参数与 readiness 标志

HOI4 的可执行文件、mod 参数形式及日志标志必须在机器 A 上做一次人工基线侦察并记录，不能只凭示例或记忆编码。基线侦察至少回答：

- 直接可执行文件路径与文件哈希；
- 实际可用的 debug/mod 启动参数数组；
- 能证明指定 mod 已加载的日志标志；
- 主菜单 ready 标志；
- 如需地图/剧本测试，剧本加载完成标志；
- 正常退出时的日志和进程退出码表现。

Gate 0 产出版本化 `baseline_contract_id`，绑定：游戏版本与 executable SHA-256、精确 argv 数组、descriptor 解析结果、整个被测 mod 内容树哈希、profile/rules 哈希、用户目录写入 allowlist、日志集合与 readiness 状态机。上述任一输入变化时旧基线自动失效，必须重新侦察。

找不到稳定标志时，执行器只能返回 INCONCLUSIVE，不能用固定等待时间伪造 PASS。

## 三、分层测试模型

执行器使用 repo 内受控 profile，不接受任意 shell 命令。

| Profile | 目标 | PASS 最低证据 | 适用任务 |
|---|---|---|---|
| `process-smoke` | 可执行文件可启动且保持存活 | 进程达到最小存活时间 + 新日志产生；报告标记 `registrable=false`，`task test-result` 必须拒绝 | T-042 自测 |
| `menu-debug` | 指定 mod 在 debug 模式进入主菜单 | mod-loaded 标志 + menu-ready 标志 + 无致命日志 | 通用模组冒烟 |
| `map-load` | 地图/历史数据完成加载 | mod-loaded + map/history-ready 标志 + 无 MAP_ERROR | T-028/T-041 |
| `scenario-load` | 指定书签/存档进入游戏世界 | 需要另行验证的自动启动参数或测试存档；v1 可保留未实现 | 后续机制测试 |

Profile 存放建议：`config/game-test-profiles.json`。其中只能声明：标志正则、最小运行时间、日志集合和超时；不得声明任意可执行命令。

## 四、本机配置设计

`.opencode/local.json` 增加可选 `game_test` 对象（仍被 gitignore）：

```json
{
  "game_test": {
    "executable_path": "D:\\Games\\Hearts of Iron IV\\hoi4.exe",
    "mod_descriptor_path": "D:\\TxGTest\\descriptor.mod",
    "default_profile": "map-load",
    "startup_timeout_seconds": 300,
    "run_seconds_after_ready": 30,
    "shutdown_grace_seconds": 15
  }
}
```

约束：

- `executable_path` 必须是 game_path 内的直接游戏可执行文件，不允许 dowser/launcher；
- `mod_descriptor_path` 必须绝对、存在、ASCII-only，且其内容/目标与仓库 `mod/descriptor.mod` 指纹一致；
- ASCII 校验必须覆盖传给游戏的路径以及 descriptor 的 `path`/`archive` 等间接引用；若使用镜像，比较整个 mod 内容树哈希而非仅 descriptor 哈希；
- 所有参数以 `subprocess.Popen(list, shell=False)` 传递，禁止 shell 字符串拼接；
- 本机绝对路径绝不进入报告、共享 JSON、命令输出或 Git。

`local.schema.json` 实现时应增加 `game_test` 子对象并 `additionalProperties=false`，防拼写错误静默生效。

## 五、命令与返回契约

建议命令：

```text
py -3 scripts/workflow.py game-test \
  --task T-028 \
  --generation 1 \
  --profile map-load \
  --report 协作/审查记录/加载测试-T028-2026-08-12.md
```

可选参数：`--startup-timeout`、`--run-seconds` 只允许在 profile 限制范围内覆盖；`--debug/--no-debug` 不在 v1 暴露，debug 由 profile 固定，避免执行者绕过测试要求。

返回码：

| 返回码 | 语义 | 是否可登记 test-result |
|---:|---|---|
| 0 | PASS | 可登记 pass |
| 1 | FAIL（有明确证据归因于被测游戏/mod 内容） | 可登记 fail |
| 2 | INCONCLUSIVE / 执行器配置错误 | 不得登记测试结果，先修执行器/环境 |

该约定与 `workflow.py main()` 当前 `WorkflowError → 2` 一致，不引入此前规划中的返回码 3。

## 六、会话状态机

```
PREFLIGHT
  ├─失败→INCONCLUSIVE
  └─通过→BASELINE_LOGS
BASELINE_LOGS→LAUNCHING
LAUNCHING
  ├─启动失败→INCONCLUSIVE
  ├─提前退出且有被测对象 fatal/crash 证据→FAIL
  ├─提前退出但归因不明→INCONCLUSIVE
  └─存活→WAITING_READY
WAITING_READY
  ├─致命日志→FAIL
  ├─进程提前退出（归因不明）→INCONCLUSIVE
  ├─超时且证据不足→INCONCLUSIVE
  └─readiness 全满足→SOAKING
SOAKING
  ├─致命日志/崩溃→FAIL
  └─时间满足→STOPPING
STOPPING
  ├─优雅终止/Job 关闭成功→VERIFY_STOPPED
  └─清理失败→INCONCLUSIVE（高优先级操作告警）
VERIFY_STOPPED
  ├─Job 仍有存活进程→INCONCLUSIVE
  └─进程树为空→COLLECTING
COLLECTING
  ├─日志无法取得一致快照→INCONCLUSIVE
  ├─本次 fatal/crash 证据→FAIL
  └─证据完整→WRITING_REPORT
WRITING_REPORT
  ├─原子写入/校验失败→INCONCLUSIVE
  └─JSON schema + Markdown 一致→PASS|FAIL|INCONCLUSIVE
```

必须使用单调时钟（`time.monotonic()`）计算超时，UTC 仅用于报告时间戳，避免系统时钟漂移破坏超时。

## 七、日志增量隔离算法

严禁清空、删除或覆盖用户日志。启动前对 profile 声明的每个日志记录：

- 是否存在；
- 文件大小；
- mtime；
- **必须**记录文件 identity（Windows file index/volume serial，无法取得则记 unknown）、创建时间、首尾小块哈希（判断截断/轮转）；
- 会话启动 UTC 与 monotonic 时间。

结束后：

1. 只有文件 identity 相同、`new_size >= old_size` 且基线尾部哈希仍能在原偏移处验证时，才读取 `[old_size:new_size]`；
2. identity 变化、尺寸缩小或尾部连续性验证失败均视为截断/替换/轮转。读取新文件全文并标记 `rotated=true`；若无法证明该文件属于本次会话则 INCONCLUSIVE；
3. 若无新增字节，记为 `no_new_evidence`，不得把旧日志当证据；
4. 在 WAITING_READY/SOAKING 期间持续轮询并维护每个文件的 identity/offset，避免多次截断后最终重新长大导致漏读；
5. 每次读取先等待文件大小在短稳定窗口内不变，遇共享冲突/短读有限重试；无法取得一致快照则 INCONCLUSIVE；
6. 二进制增量在首尾按换行边界拼接残片，避免偏移落在半行/多字节字符中间；固定解码顺序（UTF-8 BOM→UTF-8→Gate 0 确认编码），记录实际编码与替换字符数；
7. 只把脱敏后的命中行与前后各一行写报告，单行和总证据长度设上限；
8. 绝对路径、用户名、Steam ID、token 形态在报告前脱敏。

建议读取：`logs/error.log`、`logs/game.log`、`logs/system.log`（最终集合由机器 A 基线确认）。同时对 `crashes/` 目录做只读前后快照；本次新增 crash 目录/转储直接 FAIL，但不提交转储。

## 八、判定模型

### PASS

必须同时满足：

1. 进程成功启动并存活到 readiness；
2. mod-loaded 必需标志全部出现；
3. profile readiness 必需标志全部出现；
4. ready 后存活达到 `run_seconds_after_ready`；
5. 本次日志增量无 fatal 命中；
6. 本次无新增 crash 证据；
7. 受控退出成功（主动 terminate 后退出码不作为崩溃）。

### FAIL

任一条件成立：

- readiness 前退出且日志/crash 证据明确归因于被测内容；归因不明则 INCONCLUSIVE；
- 本次新增 crash 证据；
- 日志增量命中经确认的 fatal 规则（fatal 优先于 ignore，不被 ignore 覆盖）；
- 明确出现 mod 加载失败或目标 profile 失败标志。

未知退出原因（DLL/运行库缺失、杀毒、权限、用户手动终止、runner 异常）不得判 FAIL，应归 INCONCLUSIVE。

### INCONCLUSIVE

- 配置/路径/权限错误；
- readiness 超时但无明确失败证据；
- 日志无新增证据；
- 日志截断/编码导致证据无法可靠解释；
- 执行器自身异常；
- 进程树清理不完整；
- 用户目录出现 allowlist 外写入。

INCONCLUSIVE 不得自动转成 FAIL，避免环境问题消耗任务失败次数。

## 九、模式与日志规则管理

日志规则分四类：

1. `required_markers`：全部出现才 ready；
2. `fatal_patterns`：命中即 FAIL；
3. `ignore_patterns`：机器 A 基线确认的良性噪声；
4. `redaction_patterns`：报告脱敏。

每条 marker 必须声明来源日志、顺序/前驱状态、大小写策略、捕获字段和最小/最大次数；支持 `invalidating_markers`（ready 后出现即使状态失效）。`mod-loaded` 必须捕获并匹配目标 mod 的稳定 ID/内容版本，不能只匹配显示名。

判定优先级：执行器/证据不可靠→INCONCLUSIVE；证据可靠且有被测对象 fatal→FAIL；所有 required 状态按序满足且无失效/fatal→PASS。ignore 规则不能覆盖 fatal，只能排除在基线中逐条确认的特定噪声。

禁止使用过宽模式（如裸 `assert`、`exception`）直接 FAIL；应包含上下文或组件限定，并用真实日志夹具验证。规则变更属于测试判定语义变化，须主 agent 审查；新增 fatal 规则应更新 T-042 决策/后续决策记录。

## 十、Windows 进程管理

- 直接启动 `hoi4.exe`，不启动 dowser，避免丢失进程所有权；
- Windows 使用标准库 `ctypes` 创建 Job Object，将根进程立即加入，并设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；Job 加入失败不得继续测试；
- 保存进程 HANDLE、PID、创建时间和 session_id，不能仅凭 PID 清理；正常路径先尝试受控终止，宽限后关闭 Job 杀死本 Job 中进程；`taskkill /PID /T /F` 仅作最后兜底且必须再次核对 PID 创建时间；
- 启动前若存在任何 HOI4 进程且日志目录未隔离，拒绝执行，避免另一实例污染日志；
- 启动前若存在有效 game-test 锁，拒绝并发；锁保存于被忽略的 `.opencode/game-test.lock`（PID、创建时间、session_id、profile），遇陈旧锁只报告，主 agent 显式清理；
- `try/finally` + `atexit` 双重清理；不得按进程名批量杀死所有 HOI4 实例；
- readiness 前进程退出，且证据归因于被测内容才判 FAIL；归因不明判 INCONCLUSIVE；runner 主动终止后的退出码不视为崩溃。

## 十一、证据与报告

每次测试生成一对文件：

- `协作/审查记录/加载测试-<task>-<timestamp>.json`：机器可读权威证据；
- 同名 `.md`：人类审查摘要，派生自 JSON。

建议新增 `schemas/game-test-report.schema.json`，字段至少包括：

- schema_version/session_id/task_id/generation/profile；
- game_version/executable_sha256/baseline_contract_id/mod_descriptor_sha256/mod_tree_sha256/git_head/git_dirty；
- runner_commit/profile_hash/rules_hash/permission_policy_id；
- started_at/ended_at/durations；
- executable basename（无绝对路径）/sanitized argv；
- readiness 标志及首次出现时间（含来源日志与顺序）；
- 进程退出原因/退出码/是否 runner 主动终止；
- 每日志 baseline/append bytes/rotated/hash；
- fatal/ignored/status 命中摘要；
- crash evidence；
- verdict（PASS/FAIL/INCONCLUSIVE）与 reasons；
- registrable（仅 menu-debug/map-load 等真实加载测试为 true）。

报告使用临时文件写入、fsync 后原子 rename；JSON 成功且通过 schema 后才渲染 Markdown。JSON→Markdown 必须可重复渲染；`validate` 校验 schema 和 Markdown 是否由当前 JSON 生成。原始日志不入库。报告含唯一 session_id，消费时记录 consumed_by_task/generation，防旧报告重放。所有输出路径（报告、命令输出、错误处理）都必须经过脱敏，禁止绝对路径/traceback 泄漏。

## 十二、任务状态机集成

v1：

1. `game-test` 要求 `--task` 对应任务处于 `pending_test`，generation 一致；工作树默认必须干净，并记录精确 mod 内容树哈希；
2. 执行器只生成报告，不修改 `tasks.json`，保持“仅主调度器登记状态”的边界；
3. 主调度器审查报告后显式执行：
   - PASS → `task test-result --result pass --report ...`
   - FAIL → `task test-result --result fail --report ...`
   - INCONCLUSIVE → 不登记结果，任务保持 pending_test；
4. `task test-result` 后续实现必须消费权威 JSON 并机器校验 task/generation/head/mod_tree/profile/verdict/registrable/session 未消费；Markdown 仅供人审；校验失败拒绝登记；
5. `process-smoke`、INCONCLUSIVE、commit/profile 不匹配或已消费报告一律拒绝登记；
6. `test-result fail` 继续走失败计数、blocked 与 checkpoint 回滚，但只有可归因 FAIL 报告可消耗失败次数。

后续可设计 `--record-result`，但必须仍由主调度器权限控制，且不能让 runner 在 INCONCLUSIVE 时改状态。

## 十五、测试矩阵

| 测试 | 预期 |
|---|---|
| 正常 ready + 无 fatal | PASS |
| readiness 前进程退出 | FAIL |
| ready 后新增 crash 目录 | FAIL |
| MAP_ERROR 仅存在于旧日志 | 不计入本次 |
| MAP_ERROR 出现在新增日志 | FAIL |
| 日志截断/轮转 | 正确读取新内容并标记 rotated |
| 日志截断后重新长到超过旧大小 | 不得从旧 offset 漏读；连续性失败则轮转处理/INCONCLUSIVE |
| 同名文件替换、多次轮转、读取中继续写 | 正确跟踪 identity/offset 或 INCONCLUSIVE |
| baseline 落在半行/多字节字符中间 | 拼接残片，不误匹配/漏匹配 |
| 无新增日志 | INCONCLUSIVE |
| readiness 超时无 fatal | INCONCLUSIVE |
| 报告路径越界 | 执行器错误，返回 2 |
| mod descriptor 非 ASCII/指纹不符 | 执行器错误，返回 2 |
| 同时启动第二会话 | 锁拒绝，返回 2 |
| 已有人工 HOI4 实例 | 未隔离日志时拒绝执行 |
| Job 加入失败/根 PID 先退出/PID 复用 | 不误杀，清理不完整则 INCONCLUSIVE |
| terminate 超时 | taskkill 仅清理本 PID 树 |
| runner 主动退出 | 不按 crash 处理 |
| task 非 pending_test/generation 错 | 拒绝执行 |
| process-smoke/旧 generation/旧 commit/已消费报告用于 test-result | 拒绝登记 |
| 用户目录出现 allowlist 外写入 | 阻断 PASS，INCONCLUSIVE + 脱敏变更摘要 |
| fatal 与 ignore 同时命中 | fatal 优先，不被 ignore 覆盖 |
| ready 后出现失效标志或停止阶段 flush fatal | FAIL |
| JSON 写入中断/Markdown 不一致 | INCONCLUSIVE；validate 拒绝 |
| readiness marker 顺序错误/来自不同加载尝试/不同实例 | 不判 PASS |

## 十六、实现验收标准

1. Gate 0 决策和机器 A 基线证据齐全；
2. 全部 fixture/进程 mock 测试在 Linux + Windows CI 通过；
3. 执行器绝不使用 `shell=True`，不接受任意命令行字符串；
4. 日志采用增量隔离，旧错误不污染本次判定；
5. PASS 必须有 mod-loaded + readiness 双证据，不能只凭存活时间；
6. 所有退出路径清理本次进程树与锁；
7. JSON 报告通过 schema，Markdown 可重复渲染且无本机绝对路径；
8. PASS/FAIL/INCONCLUSIVE 与任务状态机行为符合第十二章；
9. 机器 A 的 `menu-debug` 和 `map-load` 实机至少重复 3 次（仅为最小冒烟门槛，不宣称统计稳定性）；同时覆盖冷启动/热启动，任一次 INCONCLUSIVE 均须调查；游戏/mod/profile/rules/基线契约变化后重新验收；
10. T-028 `pending_test` 端到端跑通。
