# 加载测试自动化规划：游戏自动化测试执行器（T-042，D-20260812-022）

> 状态：已规划｜本次仅登记任务与规划，不实现。实现留待后续独立任务。

## 一、目标

在机器 A（full）上建立**启动→进入→调试→运行→退出→日志解析**的自动化闭环，使 `requires_load_test=true` 的任务（如 T-028）可自动生成结构化加载测试证据，供 `task test-result` 消费；消除当前"人工启动游戏+手写报告"的环节。

## 二、现状与边界

- **已有**：`load_test` 能力探测（workflow.py:1161，检查游戏可执行文件 + 用户文档目录存在）；`requires_load_test=true` 状态机门禁（验证通过强制进入 pending_test）；`-debug` 启动项知识（docs/mod_examples/01:85：热加载、MAP_ERROR 才记录、nudge、GUI 悬停）。
- **缺失**：启动/进入/调试/退出/日志解析的执行器；进程管理；日志解析规则。
- **边界**：`game-test` 是探测成立后的**执行器**，与能力探测分离；不改动 load_test 探测逻辑。

## 三、命令设计（`workflow.py game-test`）

```
python3 scripts/workflow.py game-test \
  --task T-028 \                  # 关联任务（可选，用于报告命名与租约校验）
  --mod-name "Tianxia et Gentes" \# mod 显示名（descriptor.mod name）
  --timeout 300 \                 # 加载+运行总超时（秒），默认 300
  --wait-load 120 \               # 等待加载完成的轮询上限（秒）
  --no-debug \                    # 可选：不加 -debug 参数（默认加）
  --report 协作/审查记录/加载测试-T028.md   # 报告输出（白名单内）
```

返回码语义（与现有门禁对齐）：
- `0`：加载成功、无致命错误（MAP_ERROR/断言失败等）→ 报告标记 `LOAD_TEST PASS`
- `2`：加载失败/致命错误/日志命中错误特征 → `LOAD_TEST FAIL`（供 test-result fail）
- `3`：执行器自身错误（参数/权限/路径）→ 不落测试结果

## 四、执行流程（七步）

1. **前置校验**：`derive_environment` 实测 `load_test=true`（复用现有能力门禁）；`game_path`/`user_docs_path` 存在；报告路径 ∈ `协作/审查记录/` 白名单（复用 `checked_report_path` 逻辑）。
2. **启动**：`subprocess.Popen([game_exe, "-debug", "-mod", "mod/<name>"], cwd=game_path)`；Windows 用 `py -3` 等价调用；记录 PID 与启动时间。
3. **等待加载**：轮询 `user_docs/logs/error.log`（存在且大小增长）与进程存活状态；超 `--wait-load` 视为加载失败。
4. **运行挂机**：等待 `--timeout` 剩余时间（或检测到"进入主菜单/加载完成"标志——v1 用固定时间窗，v2 可加日志标志解析）。
5. **退出**：先发 `terminate()`，宽限 10 秒后 `kill()`；确保无僵尸进程；记录退出码。
6. **日志解析**：读取 `logs/error.log`（`-debug` 下 MAP_ERROR 才记录）与 `logs/game.log`（若存在）：
   - 致命特征：`MAP_ERROR`、`Assertion failed`、`has game error`、`exception`、`crash`
   - 状态特征：`Loading History`、`Creating Map`、`Launched`（加载进度）
   - 输出：命中数、特征行原文（脱敏截断）、日志总行数。
7. **报告生成**：写 `协作/审查记录/加载测试-<task>.md`（固定模板：任务/时间/命令/进程退出码/加载耗时/特征命中/结论 PASS|FAIL），返回码按上述语义。

## 五、日志解析规则（v1 最小集）

| 特征 | 严重度 | 动作 |
|---|---|---|
| `MAP_ERROR` | 致命 | FAIL |
| `Assertion failed` / `assert` | 致命 | FAIL |
| `exception` / `crash` / `fatal` | 致命 | FAIL |
| `Loading History` / `Creating Map` | 状态 | 记录进度时间戳 |
| 空日志 / 日志不存在 | 异常 | FAIL（无证据） |

规则集中定义为常量表（`LOAD_TEST_FATAL_PATTERNS`），可测试、可扩展；不做启发式猜测。

## 六、与任务状态机的集成

- 主调度器：`task test-result --result pass|fail --report <报告>` 消费 game-test 产物（现有命令，无需改动）。
- 失败语义：`test-result fail` → `reopen_task(stage="test")` → 失败计数/超限 blocked/回滚机制全部沿用。
- 报告命名：`协作/审查记录/加载测试-<TASK ID>-<日期>.md`；`checked_report_path` 白名单校验保证路径安全。
- 关联任务校验（v2 可选）：`--task T-028` 时校验任务处于 pending_test 且代数有效，防止无任务乱跑。

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| 游戏启动时间长/首次启动着色器编译 | `--wait-load` 可配置；报告记录实际耗时 |
| 进程失控/挂死 | terminate→kill 两级退出 + 总超时；`atexit` 兜底 |
| 日志路径/编码差异（Windows 中文用户目录） | 只读用户目录 `logs/`；UTF-8 读取容错（errors="replace"） |
| 误判（mod 正常但日志有良性警告） | 致命特征白名单最小化 + 报告展示原文供人工复核 |
| 游戏本体安全 | 执行器只读 game_path 与 user_docs；不修改任何本体文件 |
| 与现有门禁冲突 | 不触碰 load_test 探测/租约/回滚逻辑；仅新增命令与报告消费 |

## 八、验收标准（实现时）

1. 机器 A 上 `game-test --no-debug --timeout 60` 能启动→运行→退出并生成报告；
2. 注入伪造 MAP_ERROR 到 error.log 夹具时返回 FAIL；
3. 空日志/无日志返回 FAIL（无证据）；
4. 报告路径越界被拒绝；
5. 全套单元测试（进程 mock + 日志解析 + 报告模板）在 CI 双平台通过；
6. T-028 的 `pending_test` 流程端到端跑通（game-test → test-result pass）。
